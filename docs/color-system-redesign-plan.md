# 品牌色表与颜色映射改造计划

## 背景

豆稿当前先从图片中提取颜色，再按顺序生成类似 `A1`、`B1` 的图纸标记，并把识别出的 HEX 值展示在颜色列表和导出图例中。这里存在一个严重的语义风险：`A1` 等标记恰好与 MARD 等品牌的真实色号形式相同，但当前实现并没有使用任何品牌色表。

这次改造的目标不是简单增加一个下拉框，而是建立三层长期稳定的数据关系：

```text
图片像素
  ↓ 识别与颜色聚类
原图颜色组 sourceColor
  ↓ 可选的品牌色表映射
目标拼豆颜色 targetColor + targetCode
  ↓ 用户校对
最终图纸与采购清单
```

图像识别和品牌匹配必须保持独立。切换品牌、匹配算法或候选色时，不得重新推测网格，也不得破坏已经提取的原图颜色组。

## 本轮范围

接下来只做以下三个方向：

1. 建立可追溯的主流品牌色表，并允许用户选择品牌；未选择品牌时按原图本色生成图纸。
2. 建立从单色距离到整套配色关系优化的匹配逻辑。
3. 优化取色、候选色、锁定映射和人工改色交互。

本轮明确不做：

- 网格识别算法升级；
- 图片样本线上采集；
- OCR 自动读取图纸上的品牌色号；
- 图生图或其他 AI 生成功能；
- 与颜色工作流无关的首页或编辑器重设计；
- 新的服务端、账号、库存或商城功能。

## 首要安全修复

完整色表接入前，先消除现有误导：

- `A1`、`B1` 等内部编号统一称为“图纸标记”；
- `#RRGGBB` 统一称为“识别色”或“HEX 参考”；
- 未选择品牌时不出现“拼豆色号”字样；
- 只有在目标颜色确实来自某个已选择色表时，才展示品牌和真实色号；
- 导出 PNG、CSV、打印图例和工程数据使用同一套术语。

以后内部标记与品牌色号使用不同字段，不能再复用同一个 `name` 或 `code` 字段表达不同概念。

## 官方数据获取决策

### 已经确定的原则

“官方色号”和“可计算颜色”分开取证：

1. 品牌官方网站、官方经销商或官方色卡负责确认色号、名称、系列、尺寸、特殊效果和在售状态。
2. 官方没有发布机器可读 RGB 时，使用许可清楚的开放数据作为屏幕近似值，并明确标注来源和可信等级。
3. 不把官网图片或 PDF 中直接吸取的像素宣传成“官方 RGB”。网页压缩、印刷色彩管理和扫描过程都可能改变颜色。
4. 不提交官方色卡图片或整份 PDF 到仓库，只保存原始链接、访问日期、版本描述和必要的规范化事实数据，除非获得明确的再分发许可。
5. 所有第三方数据固定为本地版本快照，网站运行时不请求第三方服务器。

### MARD 的现实结论

目前已经确定“怎么取”，但还没有得到 MARD 厂商发布的官方机器色值。第一版不能等待一个可能不存在的官方 RGB 文件，也不能把社区数据冒充官方数据。

对 BeadColors 中的 MARD CSV 进行结构核对后，可以确认它足够支持第一版开发：

- 共 291 条色号与 RGB 记录；
- 基础系列为 A 26、B 32、C 29、D 26、E 24、F 25、G 21、H 23、M 15，共 221 色；
- 扩展系列为 P 23、Q 5、R 28、T 1、Y 5、ZG 8，共 70 色；
- 221 基础色和 291 完整色可以从同一份数据稳定拆分，不需要维护两份互相独立的 RGB；
- 数据中的名称目前只是重复色号，没有中文颜色名、材质效果、在售状态或测色条件。

这里的“完整”只表示常见 MARD 221/291 色号体系在数据结构上闭合，并不表示 RGB 已得到厂商测色认证。正式导入时仍要通过色号唯一性、字段范围和系列数量自动测试。

因此采用以下处理：

- 无品牌模式作为初始默认，MARD 221 作为品牌列表中的首个选项；
- MARD 291 使用同一份 MIT 数据生成，作为可选扩展色表；
- 色号体系与 RGB 数据都记录来源；
- 界面明确说明屏幕色仅用于近似匹配，采购以色号为准；
- 本轮不从官方图片或 PDF 中直接取色，也不因此阻塞 v70；
- 如果未来得到厂家数据或完成统一条件下的实物测色，作为新色表版本发布，不静默覆盖旧工程使用的色表。

- 核对 Hama、Artkal、Perler 等社区色表与品牌当前目录的差异，并在未来以新版本更新，不阻塞本轮接入。
- 评估帮助 BeadColors 补充数据、改进版本管理或建立 GitHub Release。

### 数据引入流程

每增加或更新一个色表，都执行以下步骤：

1. 在数据来源清单登记网址、发布日期或页面年份、访问日期、许可和用途。
2. 固定开放数据的上游提交版本，不跟随上游自动更新。
3. 将原始数据保存为可审计的本地固定快照，并在读取时规范化为项目自己的对象结构。
4. 检查色号唯一性、RGB 范围、系列数量、缺失字段和重复颜色。
5. 将颜色数量与官方页面逐项核对，记录缺失、停产和地区差异。
6. 抽查每个系列的浅色、中间色、深色和特殊色。
7. 更新第三方数据声明、测试和版本迭代记录。

### 上游依赖与自动更新策略

BeadColors 当前没有 GitHub Release 或稳定版本标签，主要通过 `master` 分支维护。Raw GitHub 允许跨域请求，但豆稿不在用户浏览器运行时直接获取远端最新数据：

- 当前 Content Security Policy 只允许连接同源；
- 运行时依赖 GitHub 会破坏离线使用；
- 国内网络对 GitHub 和 Raw GitHub 的访问不够稳定；
- 上游无提示修改会让同一个工程在不同日期得到不同色号；
- Service Worker 难以同时保证最新数据、离线回退和工程可复现性。

采用“固定快照 + 更新检查”的依赖方式：

1. 将选定上游提交中的原始 CSV 固定到 `bead-palettes.js`，连同来源提交 SHA 一起提交到豆稿仓库。
2. Cloudflare Pages 始终构建仓库内已经审核的快照，不在构建时盲目跟随 `master`。
3. `npm run check:beadcolors` 比较本地固定提交和上游 `master`，只报告差异，不写文件。
4. 手动触发及每周定期运行的 GitHub Actions 执行同一检查。
5. 发现更新后，由维护者人工检查色号新增、删除、RGB 变化、许可和测试结果。
6. 审核通过后再更新本地快照、数量断言和 revision；不由 CI 自动修改生产分支。

如果 BeadColors 以后发布正式 Release，更新脚本优先跟踪 Release tag；在此之前使用精确 commit SHA，不使用浮动的 `master` URL作为生产数据版本。

## 色表数据结构

当前落地结构：

```text
bead-palettes.js
color-matching-core.js
THIRD_PARTY_NOTICES.md
scripts/
  check-beadcolors.mjs
tests/
  bead-palettes.test.mjs
  color-matching-core.test.mjs
```

色表级字段：

```text
schemaVersion
paletteId
brand
series
region
beadSize
revision
displayName
sourceIds
rgbQuality
lastVerified
```

颜色级字段：

```text
code
name
srgb
finish
active
officialSourceId
rgbSourceId
notes
```

其中：

- `finish` 至少区分 `opaque`、`transparent`、`neon`、`pearl`、`glitter`、`glow` 和 `metallic`；
- `rgbQuality` 区分 `official-digital`、`measured`、`community` 和 `estimated`；
- Lab、OKLab 等派生值由同一套代码从 sRGB 计算，避免在多个文件中保存互相矛盾的数值；
- 工程数据保存 `paletteId + revision`，保证旧工程以后仍能解释当时使用的色号。

不预先保存每两个品牌之间的完整映射表。跨品牌转换由统一色彩空间和匹配引擎动态生成，避免品牌增加后形成大量难以维护的两两关系。

## 状态模型

每个颜色组至少保留：

```text
marker        图纸内部标记
sourceColor   从原图提取或由用户重新吸取的颜色
targetColor   当前用于图纸预览的颜色
targetCode    选择品牌后对应的真实色号
paletteId     当前品牌色表
matchMethod   本色、自动匹配或人工指定
locked        是否禁止自动重算覆盖
```

规则：

- 无品牌模式下 `targetColor = sourceColor`，`targetCode = null`；
- 选择品牌后只计算 `targetColor` 和 `targetCode`；
- 用户吸取原图颜色修改的是 `sourceColor`；
- 用户搜索或选择色号修改的是 `targetColor + targetCode`；
- 自动参数变化只重算未锁定的目标映射；
- 切换到另一个品牌时，旧品牌色号不能继续冒充有效结果。

拟定版本：v70。

- 建立色表 schema、来源清单和校验测试；

## 阶段二：颜色匹配逻辑

拟定版本：v71。

详细实现方案见《[品牌颜色匹配技术设计](color-matching-technical-design.md)》。

### 基线算法

先实现可解释的逐色基线：

1. 将原图色和品牌色转换到统一色彩空间；
2. 使用 CIEDE2000 生成每个原图颜色的前若干候选；
3. 记录最佳色差、候选差距和低可信提示；
4. 对透明、珠光、夜光等特殊效果使用独立资格规则，而不是与普通不透明色混排。

逐色 CIEDE2000 只是基线，不是最终方案。它能改善单个颜色的感知距离，但仍可能让一组颜色分别向不同方向偏移，破坏原画的配色关系。

### 全局关系保持

最终匹配同时考虑：

- 单色距离；
- 原图颜色之间的亮度、色相和饱和度关系；
- 两种颜色在图中相邻的频率；
- 各颜色的豆子数量；
- 明暗顺序是否反转；
- 原本明显不同的颜色是否被不合理合并；
- 用户已经锁定的映射。

可以把原图调色板视为图结构：

- 节点是颜色组，权重是使用量；
- 边是画面中的相邻关系，权重是相邻次数；
- 匹配目标是从每个节点的少量候选中，选出整体关系最协调的一组品牌色。

第一轮实现采用“前 K 个候选 + 局部交换或束搜索”，不直接引入大型模型。正常拼豆图的颜色数量较少，这种方法适合纯前端运行；性能不足时再移入 Web Worker。

### 实验与指标

正式替换前，在独立颜色实验页并排比较：

- RGB 欧氏距离；
- CIEDE2000 逐色最近；
- 全局关系保持映射；
- 人工参考选择。

至少记录：

- 加权平均单色差；
- 相邻颜色关系失真；
- 明暗顺序反转次数；
- 不合理颜色合并次数；
- 用户最终保留自动首选的比例；
- 典型手机和桌面设备耗时。

## 阶段三：取色与改色交互

拟定版本：v72。

颜色条目的主要结构：

```text
原图颜色 │ 无缝接缝 │ 当前拼豆颜色  品牌色号
                         候选色列表
```

主要能力：

- 原图颜色与目标豆色无缝并排，帮助观察接缝和偏色方向；
- 展示品牌、色号、名称、候选顺序和匹配可信度；
- 从原图重新吸取 `sourceColor`；
- 从当前品牌色表搜索或选择 `targetCode`；
- 锁定满意的映射，重算时只处理未锁定颜色；
- 重置单个颜色或全部自动匹配；
- 合并、拆分、新增和删除颜色组；
- 修改后实时更新整张图纸与采购统计；
- 手机端不依赖悬停，候选列表和吸管操作有足够触控尺寸。

颜色列表不能成为唯一判断依据。用户选择候选时，同时看到原图预览和目标图纸预览；算法的全局优化结果也允许被人工审美覆盖。

## 测试策略

### 数据测试

- schema 版本和必填字段；
- 色号唯一、RGB 数值合法；
- 系列数量与来源记录一致；
- 特殊效果分类完整；
- 来源和许可声明不缺失；
- 旧工程引用的色表版本仍可读取。

### 算法测试

- 单色候选排序固定；
- 无品牌模式完全不量化颜色；
- 已锁定映射不会被重算；
- 两个相近原色允许合理合并，两个承担轮廓差异的颜色不会轻易合并；
- 全局算法不会为了关系协调选择单色差极端离谱的候选；
- 同一输入在桌面端和手机端得到相同结果。

### 交互与导出测试

- 品牌切换、撤销、重做和工程数据恢复；
- 吸取原色与指定品牌色号互不混淆；
- PNG、CSV、打印图例和 JSON 对同一颜色使用相同色号；
- 手机端候选选择、锁定和重置可操作；
- Service Worker 升级后不会混用旧代码与新色表。

## 版本与文档制度

从本计划开始，每个阶段都必须留下：

1. 计划或设计文档中的决策更新；
2. `CHANGELOG.md` 中的用户可感知变化；
3. 数据来源和上游版本；
4. 自动测试与人工验证结果；
5. 一个阶段完成并经用户验收后再做本地提交；
6. 用户确认后再推送发布。

拟定迭代：

| 版本 | 主题 | 发布条件 |
| --- | --- | --- |
| v70 | 色表基础、术语和品牌选择 | MARD 221 来源、测试、导出和无品牌模式全部正确 |
